# 서론

## 무엇을 만드는가

학습자가 강의를 보다 막혔을 때 질문에 답하는 AI 튜터다. 한 문장으로 하면 **학습자 질문을 받아 해당 강의 내용에서 근거를 찾아 그 근거를 인용해 답하고, 근거가 없으면 답하지 않는 서비스**다.

## 왜 만드는가

학습자가 막히면 갈 곳이 셋이다. 강사에게 남기면 답이 몇 시간에서 며칠 뒤고 그동안 학습이 멈춘다. 검색하면 강의와 다른 버전과 다른 용어가 나오는데 초심자는 그 차이를 판별하지 못한다. 그냥 넘어가면 이해 공백이 쌓인다. 셋 다 학습으로 돌아오지 않는다.

원인은 강의 내용이 영상 안에 갇혀 있어서 질문에 답할 형태로 존재하지 않는 것이다. 그래서 이 문제는 새 지식을 공급하는 문제가 아니라 **있는 지식을 꺼내는 문제**로 본다. 전자로 보면 좋은 모델을 고르는 게 답이 되고, 후자로 보면 검색 구조를 세우는 게 답이 된다.

## 어려운 쪽은 답하는 게 아니라 안 답하는 것이다

문서 챗봇을 그냥 붙이면 세 가지가 무너진다. 검색이 빗나가도 답을 만들고, 모른다고 말하지 못하고, 미션 정답을 그대로 흘린다. 셋 다 검색 이후에는 손쓸 방법이 없다. 조각이 프롬프트에 들어간 뒤에는 되돌릴 수 없다.

그래서 설계 원칙이 셋이다. 검색 결과를 믿지 않는다, 모름을 정식 응답으로 만든다, 미션 질문은 답이 아니라 힌트로 돌린다. 이 셋을 빼면 남는 게 단순 RAG 뿐이라 만들 이유가 없다.

## 오늘의 목표

이틀 안에 원칙 셋이 실제로 도는 것을 보이는 것이 목표다. 그러려면 인증, 서비스 디스커버리, compose 통합, CI 를 다 붙일 시간이 없다. 자르는 대신 순서를 미루고, 되살릴 순서를 문서에 못박는 방식을 택했다.

# 본론

## 1. 착수 전 맹점 점검과 범위 결정

**What.** 코드를 쓰기 전에 기획 문서 다섯 개와 실제 코드베이스를 대조해 어긋난 지점 일곱 개를 찾아 확인 질문으로 돌렸다.

**How.** 4단계 문서가 전제한 스택(Keycloak, config-server, Zipkin, consul-1)이 로컬에 있는지 확인했다. 처음 본 `lxp-msa` 에는 없었고, 사용자가 알려준 5기 저장소를 클론해서 대조하니 전부 실물과 맞았다. 다만 결정 번호는 문서가 최신 D-66 이라고 한 것과 달리 D-67 까지 있었고, 4.5 계획이 가리킨 09장 `03_routing_pitfalls` 는 존재하지 않는 디렉터리였다.

**Why.** 4단계 문서와 4.5단계 문서가 정면으로 충돌하고 있었다. 앞은 인증과 Consul 을 완료 조건으로 걸고, 뒤는 그것을 전부 잘라낸다. 어느 쪽 기준으로 완료를 판정할지 정하지 않으면 완료 조건 자체가 없는 상태로 구현에 들어가게 된다. 사용자가 축소안을 택했고, 그 결정이 이후 모든 판단의 기준이 됐다.

## 2. S0 뼈대: FastAPI 껍데기와 신뢰 경계

**What.** `/health` 와 `/api/ai/ping` 만 있는 FastAPI 서비스를 만들었다. AI 는 넣지 않았다.

**How.** 레퍼런스(`19_langchain/11_serving_ops`)의 디렉터리 구조를 따르되 LangChain 계열 의존성은 넣지 않았다. `lifespan` 은 색인이 없으면 경고만 남기고 뜬다. `GEMINI_API_KEY` 와 `LANGSMITH_API_KEY` 에 기본값을 줘서 `.env` 없이도 서버가 뜬다.

**Why.** AI 를 같이 붙이면 401 이 났을 때 인증 문제인지 그래프 문제인지 알 수 없다. 껍데기가 도는 것을 먼저 확인해야 이후 문제의 출처가 갈린다. 키를 필수 필드로 두면 키가 없을 때 모듈 임포트 시점에 예외가 나서 서버가 아예 안 뜨는데, 그러면 서버가 뜬다는 완료 조건을 확인할 수단이 사라진다. 빈 값 검사는 없앤 것이 아니라 실제로 모델을 부르는 자리로 옮겼다.

## 3. 신뢰 경계를 한 함수로 고정

**What.** `require_member_id()` 하나에만 `X-Member-Id` 를 읽는 코드를 두고, 엔드포인트가 헤더를 직접 못 읽게 했다. 지금은 검증 없이 그대로 믿는다.

**How.** FastAPI 의존성으로 만들고 헤더 누락을 422 가 아니라 401 로 돌려준다. 파일 상단에 나중에 검증할 셋(서명, issuer, `aud` 에 `lxp-internal` 포함)을 적어 뒀다.

**Why.** 인증을 미루기로 한 이상 헤더를 그냥 믿는 코드는 어디엔가 남는다. 문제는 그것이 엔드포인트마다 흩어지는 것이다. 흩어지면 나중에 JWKS 검증으로 바꿀 때 한 곳만 빠뜨려도 그 경로로 8086 직접 호출이 통과한다. **빠뜨려도 그 엔드포인트는 200 을 잘 돌려주므로 아무 에러가 나지 않는다.** 5기 저장소가 D-33 에서 Java 쪽에 `common-security` 로 막아 둔 구멍이고, Python 은 그 모듈을 쓸 수 없다. 401 로 통일한 것도 같은 이유로, 교체 전후에 클라이언트가 보는 계약이 달라지면 분기를 두 번 고쳐야 한다.

## 4. 저장소 편입과 결정 번호 분리

**What.** 별도 저장소로 가려던 계획을 바꿔 기존 저장소 안 `ai-service/` 폴더로 넣었다. 결정 기록은 루트의 `D-nn` 과 겹치지 않게 `AI-nn` 으로 매겼다.

**How.** 5기 저장소를 클론하고 그 안으로 코드를 옮긴 뒤 `feat/` 브랜치를 팠다. 루트 파일은 하나도 건드리지 않았고, 대신 붙일 때 고쳐야 할 루트 파일 다섯 개를 목록으로 남겼다.

**Why.** 저장소를 나누면 결정 기록과 compose 가 두 벌이 된다. 이 팀은 D-66 에서 `compose.demo.yaml` 이 저장소에 없는 경로를 가리켜 화면이 조용히 안 뜨는 사고를 이미 겪었다. 결정 번호를 나눈 이유는 D-68 이 조직 규정 QA 챗봇에서 한 번 쓰이고 되돌려진 번호라 기록상으로만 비어 있기 때문이다. 그 작업이 다시 올라오면 한 번호를 두 결정이 나눠 갖게 된다. 루트를 안 건드린 것은 `AGENTS.md` 가 파일 수정에 승인을 요구하고, 뼈대 단계에서 루트를 고쳐 봐야 아직 쓰지 않을 설정만 늘기 때문이다. 안 한 것과 잊은 것을 구분하려고 목록을 남겼다.

## 5. S1 색인 원본: 제한 조각을 만드는 것이 목적

**What.** 부트캠프 학습 자료를 색인 원본 규약으로 옮기는 스크립트를 만들었다. 104파일(공개 73, 제한 31), 62만자가 나왔다.

**How.** 절의 `readme.md` 는 교안(공개)으로, 예제 `.py` 의 docstring 은 미션 설명(공개)으로, 코드 본문은 모범답안(제한)으로 갈랐다. 프론트매터에 `courseId`, `visibility`, `lang`, `version` 을 붙이고 판별 리포트를 출력한다.

**Why.** 분량보다 **제한 조각이 생기는지**가 중요하다. 모범답안에 해당하는 문서가 하나도 없으면 미션 정답을 흘리지 않는가를 검증할 대상 자체가 없다. 유출을 막는 기능은 막을 것이 있어야 검증된다. docstring 은 무엇을 만드는지고 코드는 어떻게 만드는지라, 그 경계가 그대로 공개와 제한의 경계가 된다. 판별 리포트에 기본값으로 떨어진 파일 수를 찍는 것은 규약을 안 지킨 원본이 있다는 신호를 놓치지 않기 위해서다.

첫 실행에서 함정 둘을 밟았다. 코드블록 안의 파이썬 주석이 H1 제목으로 잡혀 `title` 에 들어갔고, 그 제목의 콜론 때문에 프론트매터 YAML 이 깨졌다. 쓰는 쪽은 멀쩡하고 읽을 때 터지는 종류다. 제목 탐색 전에 코드 펜스를 걷어내고, 문자열 조립 대신 `yaml.safe_dump` 를 쓰도록 고쳤다.

## 6. S1 색인 적재: 분할 규칙과 두 번의 실패

**What.** 교안을 조각 633개(공개 537, 제한 96)로 나눠 Chroma 에 적재했다.

**How.** 제목 경계로 먼저 나누고 길이는 나중에 본다. 코드 블록은 상한 1200자를 넘어도 자르지 않고, 조각 앞에 제목 경로를 붙인다. 하한 미만은 같은 제목 경로일 때만 앞 조각에 병합한다. `--dry-run` 으로 분포를 먼저 보고 적재한다.

**Why.** 길이를 먼저 보면 문장 중간에서 잘려 조각 하나만으로 뜻이 안 통한다. 코드 블록 예외는 반쪽 코드가 근거로 인용되면 학습자가 동작하지 않는 코드를 보게 되기 때문이고, 이것은 길이 규칙보다 우선한다. 제목 경로를 붙이는 이유는 겹침 설명 같은 문장이 그 자체로는 어느 강의 이야기인지 알 수 없어 다른 강의의 비슷한 문장과 구분되지 않기 때문이다.

실패가 둘 있었다. 첫 `--dry-run` 에서 코드 블록이 아닌데 상한을 넘은 조각이 13개 나왔다. 제목 경로 접두사를 조각을 묶은 **뒤에** 붙여서 길이 계산에 안 들어갔고, 하한 병합도 상한을 보지 않았다. 접두사 길이를 뺀 예산으로 묶도록 고쳐 13개가 0개가 됐다.

두 번째는 실제 적재 중 50/633 에서 난 429 오류다. 배치 50 짜리 요청 **2건**에서 터졌으니 요청 수 기준이라면 걸릴 수가 없다. 조각으로 세면 50+50=100 이고 무료 등급 한도와 맞는다. 요청 수로 오해했다면 배치만 계속 줄였을 텐데, 배치를 줄여도 분당 총 조각 수는 그대로라 계속 막혔을 것이다. 배치 25 와 분당 90 조각으로 간격을 두고 429 면 65초씩 늘려 재시도하도록 고쳤다. 실제 실행에서 재시도가 7번 걸렸고 전부 회복해 633/633 이 들어갔다.

## 7. 반쪽 색인이 준비된 것으로 보인 문제

**What.** 429 로 죽은 뒤 `/health` 가 `index_ready: true` 를 돌려줬다. 실제 색인은 50/633 이었다.

**How.** 색인이 끝까지 갔을 때만 `data/chroma/.complete` 표시를 남기고 `/health` 가 그것을 보게 바꿨다. 다시 만들기 전에 표시부터 지운다.

**Why.** 원인은 디렉터리 존재만 보고 판정한 것이다. 조각이 몇 개든 디렉터리는 있다. 이 상태가 나쁜 이유는 서버가 멀쩡하고 검색만 대부분 빈손으로 오는 형태여서, 나중에 왜 자꾸 모름 응답이 나오는지로 헤매게 되기 때문이다. 이 팀이 D-62 에서 정리한 검사하지 않은 것은 통과한 것처럼 보인다가 그대로 재현된 경우다. 표시를 지우는 순서가 먼저인 이유는, 나중에 지우면 재색인 도중에 뜬 서버가 준비됐다고 답하기 때문이다.

## 8. 검색 확인: 대조군이 있어야 검증이다

**What.** 질의 하나를 넣어 학습자 검색과 필터 없는 검색을 나란히 보는 스크립트를 만들었다.

**How.** `learner_filter` 를 `rag.py` 한 곳에 두고 Chroma 질의 조건으로 건다. 확인 스크립트는 같은 함수를 쓴다.

**Why.** 학습자 검색에서 제한 조각 0건만 확인하면 부족하다. 0건이 나오는 경우가 둘이기 때문이다. 필터가 막았거나, 애초에 걸릴 제한 조각이 없었거나. 후자라면 원칙 3 을 검증한 것이 아니라 시험을 안 본 것이다. 실제 결과에서 겹침을 묻는 질의에 대조군이 `missions/m-04/solution.md#0` 을 유사도 0.733 으로 3위에 올렸고, 학습자 검색은 0건이었다. 필터가 없었으면 그 모범답안이 그대로 프롬프트에 들어갔다는 뜻이다.

필터를 질의 조건으로 거는 이유는 가져온 뒤 걸러내면 조각이 이미 프로세스 안에 들어와 있어 로그나 예외 메시지로 샐 자리가 늘고, 거르는 자리가 여러 곳이면 한 곳만 빠뜨려도 뚫리기 때문이다.

## 9. S2 최소 그래프

**What.** START → retrieve → generate → END 직선 그래프를 만들었다. 질문 하나가 답변으로 나온다.

**How.** `TutorState` 를 TypedDict 로 선언하고 리듀서는 붙이지 않았다. `generate` 는 모델을 부르지 않고 검색된 조각을 그대로 잇는다. 확인은 `scripts/ask.py` 로 한다.

**Why.** 세 가지 판단이 들어 있다.

`generate` 에 지금 제대로 된 프롬프트를 붙이면 검색이 빗나가도 답이 그럴듯해서 무엇이 잘못됐는지 눈치채지 못한다. 답변이 3720자짜리 조각 덩어리인 것은 의도한 상태다.

그래프를 직선으로 둔 것은 분기(S3)와 루프(S4)를 같이 붙이면 답이 이상할 때 분기 판정이 틀린 건지 루프가 잘못 도는 건지 못 가리기 때문이다.

리듀서를 안 붙인 것은 덮어쓰기가 이 경우에 맞기 때문이다. 재검색하면 이전 결과는 버려야 하는데, 누적하면 품질 판정에서 부족하다고 버린 조각이 근거로 남는다. `question` 과 `search_query` 를 나눈 것도 같은 계열로, 하나로 두면 재작성이 원문을 덮어써서 학습자가 하지 않은 질문에 답하게 된다.

## 10. 문서와 협업 산출물

**What.** 이슈 1개와 PR 4개를 올리고 그중 3개를 머지했다. 결정 기록 AI-01 부터 AI-07, 작업 현황, 실행 가이드, 슬라이스별 퀴즈를 남겼다.

**How.** PR 은 저장소의 `PR_STRATEGY.md` 를 따라 쪼갰다. 한 브랜치 840줄은 과대 기준 400줄을 넘어서 계층 축(뼈대, 데이터, 색인, 그래프)으로 갈랐고, 스택 PR 로 base 를 앞 브랜치에 걸어 각 diff 에 자기 변경분만 나오게 했다.

**Why.** 리뷰어가 한 번에 판단할 수 있는 크기여야 리뷰가 형식적으로 흐르지 않는다. 500줄짜리 PR 은 승인만 받고 50줄짜리는 실제 지적을 받는다.

여기서도 실수를 하나 했다. 첫 PR 을 `--delete-branch` 로 머지했더니 GitHub 이 다음 PR 을 리타겟하지 않고 닫아 버렸다. base 브랜치가 사라져서다. 닫힌 PR 은 base 가 없으면 reopen 도 막혀서, 브랜치를 되살린 뒤 reopen 하고 base 를 main 으로 바꿔 머지했다. 스택 PR 은 전부 머지한 뒤에 브랜치를 지워야 한다.

작업 중 사용자 지적으로 문체도 고쳤다. 줄표 61개를 걷어내고, 뻔한 변경까지 정당화하던 문장 구조를 줄였다. 같은 실수를 반복하지 않도록 `CLAUDE.md` 에 글쓰기 규칙으로 남겼다.

# 결론

## 오늘 도달한 지점

서비스가 뜨고, 교안 633조각이 색인돼 있고, 질문 하나가 그래프를 통과해 근거와 함께 나온다. 설계 원칙 셋 중 **미션 정답 차단의 둘째 겹인 `visibility` 필터가 숫자로 검증됐다.** 대조군에서 모범답안이 3위로 올라오는데 학습자 검색에서는 0건이라는 것이 그 증거다.

## 아직 없는 것

품질 판정이 없어서 검색이 빗나가도 그대로 답한다. 모름 응답 경로가 없다. 의도 분류가 없어서 정답 요구를 가려내지 못한다. 답변 생성에 모델을 쓰지 않는다. 원칙 셋 중 둘이 아직 코드에 없는 셈이고, 그것이 S3 부터의 작업이다.

기존 LXP 스택과는 연결되지 않는다. 인증, Consul 등록, compose, CI 를 미뤘고 되살릴 순서를 문서에 적어 뒀다. 그중 CI 스테이지가 조용히 나쁘다. 저장소에 있는데 CI 가 한 번도 안 보는 폴더가 되기 때문이다.

## 오늘 배운 것

세 번 다 같은 형태였다. **틀렸는데 에러가 안 나는 상태**가 가장 비싸다.

프론트매터 YAML 이 깨졌을 때 쓰는 쪽은 정상이었다. 반쪽 색인은 `/health` 가 준비됐다고 답했다. 429 는 배치만 줄이면 될 것처럼 보였다. 셋 다 눈에 보이는 신호가 없었고, 확인 절차를 따로 만들어야 드러났다. `--dry-run` 의 두 숫자 비교, `.complete` 표시, 검색 확인의 대조군이 각각 그 절차다.

신뢰 경계를 한 함수로 모은 것도 같은 판단에서 나왔다. 인증을 빠뜨린 엔드포인트는 200 을 잘 돌려주므로 아무도 모른다.
