# 서론

## 무엇을 만들었나

학습자 질문에 강의 내용을 근거로 답하고, **근거가 없으면 답하지 않는** 서비스다.

## 왜 그것이 어려운가

답하는 것은 어렵지 않다. 어려운 것은 답하지 말아야 할 때 답하지 않는 것이다.
문서 챗봇을 그냥 붙이면 셋이 무너진다.

| 무너지는 것 | 왜 |
|---|---|
| 검색이 빗나가도 답을 만든다 | 유사도 높은 조각과 답이 든 조각은 다르다. 인용이 붙어 있어 학습자는 더 믿는다 |
| 모른다고 말하지 못한다 | 검색은 관련 없어도 가장 유사한 것을 돌려준다. 구조상 침묵할 방법이 없다 |
| 미션 정답을 흘린다 | 검색 품질이 좋을수록 정답을 더 잘 찾아온다 |

셋 다 검색 이후에는 손쓸 수 없다. 그래서 설계 원칙이 셋이고, 이번 작업은 그 셋이
실제로 도는지를 숫자로 확인하는 것이 목표였다.

## 최종 지표 (평가셋 50문항)

| 지표 | 목표 | 결과 |
|---|---|---|
| 근거 인용률 | 100% | 100% |
| 근거 적중률 | 80% 이상 | 100% |
| 모름 응답 정확도 | 90% 이상 | 93% |
| 미션 정답 유출 | 0건 | 0건 |
| 응답 시간 | 참고 | 평균 9.5초 최대 33.2초 |

넷 다 목표를 넘겼다. **다만 모름 응답 정확도는 한때 100% 였다가 93% 로 내려온 값이다.**
이유는 본론 B 에 적는다.

# 본론 A. 이틀 계획 구현 (S0~S9)

## A-1. 착수 전 맹점 점검

**What.** 코드를 쓰기 전에 기획 문서 다섯 개와 실제 저장소를 대조해 어긋난 지점
일곱 개를 찾아 질문으로 돌렸다.

**How.** 4단계 문서가 전제한 스택(Keycloak, config-server, Zipkin)이 로컬에 있는지
확인했다. 처음 본 저장소에는 없었고, 5기 저장소를 클론하니 전부 맞았다.

**Why.** 4단계 문서와 4.5단계 문서가 정면으로 충돌했다. 앞은 인증을 완료 조건으로
걸고 뒤는 그것을 잘라낸다. 어느 쪽으로 "완료" 를 판정할지 정하지 않으면 완료 조건
자체가 없는 상태로 구현에 들어간다.

## A-2. 뼈대와 신뢰 경계 (S0)

**What.** `/health` 와 `/api/ai/ping` 만 있는 FastAPI 서비스. AI 는 넣지 않았다.

**How.** `require_member_id()` 한 함수에만 `X-Member-Id` 를 읽는 코드를 두고,
엔드포인트가 헤더를 직접 못 읽게 했다. 헤더 누락은 422 가 아니라 401 로 돌려준다.

**Why.** AI 를 같이 붙이면 401 이 났을 때 인증 문제인지 그래프 문제인지 모른다.
인증을 미루면 헤더를 믿는 코드는 어디엔가 남는데, 그것이 엔드포인트마다 흩어지면
나중에 한 곳만 빠뜨려도 뚫린다. **빠뜨려도 200 을 잘 돌려주므로 아무 에러가 없다.**
401 로 통일한 것은 교체 전후로 클라이언트가 보는 계약을 같게 하려는 것이다.

## A-3. 색인 (S1)

**What.** 학습 자료 104파일을 조각 634개(공개 · 제한)로 나눠 Chroma 에 적재.

**How.** 절의 `readme.md` 는 교안(공개), 예제 `.py` 의 docstring 은 미션 설명(공개),
코드 본문은 모범답안(제한)으로 갈랐다. 분할은 제목 경계를 먼저 보고 길이는 나중에
본다. 코드 블록은 상한을 넘어도 자르지 않는다.

**Why.** 분량보다 **제한 조각이 생기는지**가 목적이었다. 모범답안에 해당하는 문서가
없으면 "정답을 흘리지 않는가" 를 검증할 대상 자체가 없다. 코드 블록 예외는 반쪽
코드가 근거로 인용되면 학습자가 동작하지 않는 코드를 보기 때문이다.

## A-4. 그래프 (S2~S6)

**What.** 노드 8개, 분기 2개, 루프 1개.

```
classify ─┬─ SOLUTION_SEEKING → hint ──┐
          ├─ OUT_OF_SCOPE → no_evidence│
          └─ 그 외 → retrieve → grade ─┼─ 충분 → generate ─┤
                          ▲            ├─ 부족·여유 → rewrite
                          └────────────┘                   ├→ guard → END
                                       └─ 부족·소진 → no_evidence
```

**How.** 슬라이스마다 하나씩 붙였다. 직선(S2) → 분기(S3) → 루프(S4) → 의도(S5) →
가드레일(S6).

**Why.** 한 번에 붙이면 답이 이상할 때 분기 탓인지 루프 탓인지 못 가린다.
`generate` 는 S5 까지 모델을 부르지 않고 조각을 그대로 이었다. 제대로 된 프롬프트를
먼저 붙이면 검색이 빗나가도 답이 그럴듯해서 눈치채지 못한다.

## A-5. 두 겹으로 막는 이유 (S5, S6)

**What.** 미션 정답 차단을 두 겹으로 만들었다. 검색 전 의도 분류와 검색 질의의
`visibility` 필터. 그 위에 출력 가드레일을 얹었다.

**How.** 정답을 요구하는 질문은 검색 자체를 하지 않고 `hint` 로 보낸다. 필터는
Chroma 질의 조건으로 건다. 가드레일은 인용 없는 답변, 제한 조각이 섞인 인용,
코드가 든 힌트를 잡는다.

**Why.** 검색 후에 막으면 정답 문서가 이미 손에 있고, 그때부터는 "참고하지 않았다"
를 보장할 방법이 없다. 필터를 가져온 뒤 걸러내지 않는 것도 같은 이유다.
가드레일을 또 두는 것은 앞 두 겹이 각각 틀릴 수 있고, 틀렸을 때 알아챌 방법이
나가는 결과물을 보는 것뿐이기 때문이다. 앞은 예방이고 뒤는 탐지다.

**검증.** `"청킹할 때 겹침을 왜 두나요"` 로 필터를 뗀 대조군을 돌리면 모범답안이
0.733 으로 3위에 올라온다. 필터를 걸면 0건이다. **대조군이 없으면 "막았다" 가 아니라
"막을 것이 없었다" 와 구분되지 않는다.**

## A-6. API 와 대화 맥락 (S7, S8)

**What.** `POST /api/ai/chat` 하나. sqlite 체크포인터로 `thread_id` 별 대화 유지.

**How.** `classify` 가 앞 대화를 보고 `standalone_question` 을 같이 돌려준다.
`new_turn()` 으로 턴마다 비울 필드를 모았다.

**Why.** 체크포인터가 지난 턴 값을 그대로 들고 온다. `retry` 가 남으면 재검색이
한 번도 안 돌고 `chunks` 가 남으면 버린 근거가 인용된다. **이어지는 것은 대화지
이번 턴 작업 상태가 아니다.**

**검증.** 같은 스레드 2턴에서 "그거 왜 필요한데요" 가
"RAG 시스템에서 청킹 전략은 왜 필요한가요" 로 풀렸다. 새 스레드에서 같은 질문은
`OUT_OF_SCOPE` 다. 대조군이 이력을 실제로 봤다는 증거다.

## A-7. 평가 (S9)

**What.** 평가셋 15문항과 지표 계산. 이후 50문항으로 확장.

**How.** JSONL 한 줄에 한 문항. 금지 문자열은 **제한 문서에만 있는 것**으로 골랐다.
문항마다 새 `thread_id` 를 쓴다.

**Why.** 공개 문서에도 있는 문자열을 금지어로 쓰면 정상 답변이 유출로 잡혀 지표가
거짓말을 한다. 고정 `thread_id` 는 지난 실행이 이어져 재현을 깨뜨린다.

# 본론 B. 측정 뒤에 드러난 것 (A1~A7)

15문항이 전부 통과했다. 그런데 **전부 통과라는 사실 자체가 신호**였다.

## B-1. 의도 분류가 하나도 일하지 않고 있었다 (A1)

**What.** `out_of_scope` 5문항이 **전부** `intent=CONCEPT` 으로 분류됐다. 원칙 2 를
두 겹으로 설계했는데 `grade` 한 겹만 일하고 있었다.

**How.** 색인 메타데이터의 `source_path` 로 강의 자료 목록을 만들어 분류 프롬프트에
넣고, 기준을 "목록에 없으면 범위 밖" 으로 바꿨다.

**Why.** 분류기가 "이 강의 범위인가" 가 아니라 "일반적인 기술 질문인가" 를 판단하고
있었다. 카프카도 쿠버네티스도 그럴듯한 기술 질문이라 전부 통과했다.

**결과.** 0/5 → 5/5. 응답 시간 평균 13.8초 → 2.8초.

## B-2. 점수 게이트가 가를 수 없다는 것 (A3)

**What.** `MIN_SCORE` 를 0.35 에서 0.65 로 올렸다.

**How.** 평가셋 전체의 검색 점수를 재는 스크립트를 만들어 분포를 봤다.

```
normal        0.728 ~ 0.823
out_of_scope  0.582 ~ 0.737     o-003(0.737) > n-003(0.728)
```

**Why.** 두 구간이 겹친다. **어떤 값도 전부 가르지 못한다.** 0.65 는 여유를 택한
값이다. 게이트를 잘못 넘기면 정상 질문이 재검색 루프로 빠져 더 비싸진다.

## B-3. 표본을 늘리자 회귀가 나왔다 (A2, A4)

**What.** 범위 밖 문항 10개를 더 만들고, 전체를 50문항으로 늘렸다.

**How.** 고칠 때 쓰지 않은 문항으로 셋을 만들었다. 강의 어디에도 없는 것, 다른
강의엔 있지만 이 강의엔 없는 것, **이 강의가 언급만 하고 설명은 안 한 것.**
평가셋 자체를 검사하는 스크립트도 만들었다.

**Why.** 문항을 만든 사람과 구현한 사람이 같으면 그 숫자는 실력이 아니라 문항의
성질을 잰 것일 수 있다.

**결과.** 25문항에서 100% 이던 근거 적중률이 50문항에서 95% 로 떨어졌다.
`n-017` "대화가 길어지면 앞부분을 어떻게 줄이나요" 가 범위 밖으로 밀렸다.
**늘리지 않았으면 못 봤다.**

## B-4. 가설이 반쯤 틀렸다 (A7)

**What.** `n-017` 을 고치려고 목차에 제목을 실었다.

**How.** 원인이 한 겹씩 뒤로 밀렸다.

| 층 | 증상 | 실제 원인 |
|---|---|---|
| 1 | 정상 질문이 밀림 | 분류 목차에 제목이 없음 |
| 2 | 색인에 제목이 없음 | `init_vectorstore` 가 `title` 을 안 실음 |
| 3 | 프론트매터부터 슬러그 | `build_corpus` 가 **H1 만** 찾는데 교안은 `## Chapter` 로 시작 |

**Why 가 틀렸다.** 나는 "둘 다 모델이 강의 내용을 모르는 데서 오니 제목을 넣으면
양쪽이 같이 준다" 고 적었다. 실제로는 이랬다.

| | `n-017` (범위 안인데 밀림) | `o-007` (범위 밖인데 통과) |
|---|---|---|
| 제목 없음 | 밀림 | grade 가 잡음 |
| **제목만 추가** | **그대로 밀림** | **분류가 잡음** |
| 제목 + 분류를 관대하게 | **고쳐짐** | grade 가 잡음 |

**고치려던 쪽은 그대로고 반대쪽만 좋아졌다.** 정보를 늘리자 모델이 더 자신 있게
판정했는데 그 자신감이 거절 쪽으로만 갔다.

두 번째 수정은 정보가 아니라 저울을 기울인 것이다. "애매하면 `CONCEPT` 으로 두고
뒤에서 다시 판정한다." 밀어내면 학습자가 답을 못 받고, 통과시키면 뒤 단계가 받아낸다.

**대가가 있었다.** 50문항 재측정에서 모름 응답 정확도가 100% 에서 93% 로 내려갔다.
`o-013` "HNSW 가 이웃 노드를 어떤 기준으로 연결하나요" 가 `ANSWER` 로 나갔다.
교안은 HNSW 를 설정값으로만 언급하고 동작은 설명하지 않는다. 분류가 통과시켰고
**`grade` 도 충분하다고 판정했다.** 두 겹이 같은 문항에서 같이 뚫렸다.

분류가 범위 밖을 잡는 비율도 14/15 에서 5/15 로 떨어졌다. 나머지는 `grade` 가
받아내지만 그만큼 느리다.

**정리하면 실패를 없앤 것이 아니라 옮겼다.** 근거 적중률 95% → 100%, 모름 응답
100% → 93%. 둘 다 목표 안이지만 트레이드오프였다는 사실이 기록되어야 한다.

# 트러블슈팅

셋을 남긴다. 순서대로 이어진다. 지표가 좋은데 설계가 반쪽이었고, 고치려고 재보니
접근 자체가 틀렸고, 고친 뒤에 원인이 세 겹 뒤에 있었다.

## 1. 지표는 100% 인데 두 겹 중 한 겹이 놀고 있었다

**증상.** 평가 15문항이 전부 목표를 넘겼다. 모름 응답 정확도 100%. 그런데
`intent` 열을 보니 `out_of_scope` 5문항이 **전부 `CONCEPT` 으로 분류**돼 있었다.

원칙 2 는 두 겹이다. 검색 전에 의도로 한 번, 검색 후에 품질 판정으로 한 번.
**분류가 하나도 못 잡았고 `grade` 가 전부 받아내고 있었다.** 결과만 맞았다.

**원인.** 분류 프롬프트가 강의에 무엇이 있는지 모르는 채로 "일반적인 기술 질문인가"
를 판단하고 있었다. 카프카도 쿠버네티스도 그럴듯한 기술 질문이라 통과했다.

**왜 중요한가.** 지표만 봤으면 못 봤다. 다섯 줄이 다 통과했으니 넘어갔을 것이다.
**두 겹으로 설계해 둔 덕에 결과가 안 무너진 채로 한 겹이 노는 상태**가 유지됐고,
그 사이 비용만 나갔다. 범위 밖 질문 하나가 검색 3회와 LLM 5회를 쓰고 18~32초 걸렸다.

**대응.** 색인 메타데이터에서 강의 자료 목록을 뽑아 분류 프롬프트에 넣고,
기준을 "목록에 없으면 범위 밖" 으로 바꿨다. 임베딩을 안 부르므로 비용이 0 이다.

| | 전 | 후 |
|---|---|---|
| 분류가 범위 밖을 잡음 | 0/5 | 5/5 |
| 응답 시간 평균 | 13.8초 | 2.8초 |
| 최대 | 32.0초 | 4.3초 |

정확도 네 지표는 그대로 두고 지연만 5배 줄었다.

## 2. 점수로는 애초에 가를 수 없었다

**증상.** 1번을 고치는 김에 `MIN_SCORE` 도 보려고 했다. 기준값이 0.35 인데
**한 번도 안 걸리고 있었다.** 무관한 질문도 0.6 을 넘었다.

**원인을 찾으려 분포를 쟀다.** LLM 을 안 부르는 스크립트라 몇 번이고 돌려도 싸다.

```
normal        0.728 ~ 0.823
out_of_scope  0.582 ~ 0.737
```

**두 구간이 겹친다.** 완전 무관한 질문(o-003, 0.737)이 정상 질문(n-003, 0.728)보다
높았다. 어떤 값을 잡아도 범위 밖을 전부 거르면 정상 질문도 걸린다.

**왜 중요한가.** 처음에는 "기준값이 낮아서 안 걸린다" 는 튜닝 문제로 봤다.
재보니 **튜닝으로 풀 수 있는 문제가 아니었다.** 점수 순서가 관련성 순서와
일치하지 않으므로, 점수는 관련성을 가르는 도구가 못 된다.

이것이 원칙 1 을 만든 이유를 그대로 보여준다. **유사도가 높은 조각과 답이 든
조각은 다르다.** 점수를 믿고 바로 생성했으면 세 질문 다 답을 지어냈을 것이다.

**대응.** 0.65 로 올리되 기대를 낮췄다. 여유를 택한 값이다. 게이트를 잘못 넘기면
정상 질문이 재검색 루프로 빠져 더 비싸진다. 이 값은 관련성 판정이 아니라
명백한 실패를 싸게 거르는 용도다. 판정은 내용을 보는 2단계가 한다.

## 3. 원인이 세 겹 뒤에 있었다

**증상.** 1번을 고친 뒤 평가셋을 50문항으로 늘렸더니 회귀가 나왔다.
`n-017` "대화가 길어지면 앞부분을 어떻게 줄이나요" 가 `OUT_OF_SCOPE` 로 밀렸다.
답은 `c-06/lessons/02-memory-strategies.md` 에 있다. **답할 수 있는 질문에
답하지 못하고 끝났다.**

**원인을 세 번 다시 찾았다.**

| 층 | 그 층에서 보이는 원인 | 고쳐도 안 됐다 |
|---|---|---|
| 1 | 분류 목차가 파일 경로뿐이다 | 제목을 넣으려 했더니 색인에 없었다 |
| 2 | 색인 메타데이터에 `title` 이 없다 | 넣고 재색인했는데 여전히 슬러그였다 |
| 3 | **프론트매터부터 슬러그였다.** 교안 변환기가 H1 만 찾는데 교안은 `## Chapter` 로 시작한다 | 여기가 진짜였다 |

```
전  title: memory-strategies
후  title: Chapter 06. 메모리와 상태 — 6.2 이력 전략
```

**왜 중요한가.** 2층에서 멈출 뻔했다. 제목을 메타데이터에 싣고 재색인까지 했는데
목차가 여전히 슬러그로 나왔다. 거기서 **"제목을 넣었는데도 안 고쳐졌다"** 로
결론 냈으면 방향을 잘못 틀었을 것이다. 한 겹 더 들어가서야 변환 단계가 나왔다.

같은 계열을 이날 세 번째 밟았다는 것도 신호였다. 코드블록 안 주석이 제목으로
잡힌 적이 있고, 그 제목의 콜론이 YAML 을 깨뜨린 적이 있다. **제목 찾는 코드가
두 파일에 따로 있는 것**이 공통 원인이다.

**대응.** 코드 펜스를 걷어내고 `^#{1,2}` 로 찾는다. 근본 대응인 코드 통합은 남겨뒀다.

**덧붙일 것.** 제목을 넣는 것만으로는 `n-017` 이 안 고쳐졌다. 오히려 반대 방향
문항이 좋아졌다. 최종적으로는 분류 지시를 "애매하면 통과시키고 뒤에서 판정한다"
로 바꿔 고쳤고, 그 대가로 모름 응답 정확도가 100% 에서 93% 로 내려갔다.
**실패를 없앤 것이 아니라 옮겼다.** 밀어내면 학습자가 답을 못 받고 통과시키면
뒤 단계가 받아내므로, 옮길 방향은 그쪽이 맞다고 판단했다.
